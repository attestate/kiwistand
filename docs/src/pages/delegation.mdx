# Delegation

So you don't have to confirm every upvote, submission and comment in your
wallet, your identity can let a second key, a signer, sign for it. The
identity approves the signer once, by signing a `delegation` message, and
from then on every message the signer signs counts as the identity's. That's
a signature, not a transaction: it costs nothing and needs no ETH. The
website creates such a signer in your browser when you enable one-tap
actions.

Any address can sign messages for itself, so a delegation doesn't decide who
may post. It decides whom a signer's messages are credited to.

- **Identity** (`identity`): the user's wallet, the address messages are
  credited to. It owns the profile and the karma.
- **Signer** (`signer`): the key on the device that signs stories, upvotes
  and comments.
- **Delegations**: the map from each signer to its identity that a node
  builds from the delegation messages (and, for the time before them, from
  [OP Mainnet](#from-op-mainnet-to-the-protocol)). A signer without an entry
  signs for itself.

## Creating a delegation

Since protocol 15.0.0, a delegation is a protocol message, signed by two
keys:

1. **The signer signs the identity.** It signs the EIP-712 message
   `Authorization(address identity,bool authorize)` with `identity` set to
   the identity's address and `authorize` to `true`, in the protocol's
   domain:

   ```js
   {
     name: "kiwinews",
     version: "1.0.0",
     salt: "0xfe7a9d68e99b6942bb3a36178b251da8bd061c20ed1e795207ae97183b590e5b",
   }
   ```

   Without a `chainId` and a `verifyingContract`, it's not the domain of the
   old Delegator3 contract, so an authorization can't be replayed into it or
   from it.

2. **The identity signs the delegation.** The message is

   ```json
   {
     "type": "delegation",
     "identity": "0xee324c588ceF1BF1c1360883E4318834af66366d",
     "signer": "0x4E774b8530d6f3A21C449A6f0D9A1229aB2b8C47",
     "authorization": "0x…the signer's signature, 65 bytes…",
     "authorize": true,
     "timestamp": 1793740000,
     "signature": "0x…the identity's signature…"
   }
   ```

   and the identity signs it as
   `Delegation(string type,address signer,bytes authorization,bool authorize,uint256 timestamp)`
   in the same domain. `identity` isn't part of the signed struct: it names
   who signed the message, and nodes check the signature against it. Unlike
   other messages, a delegation isn't signed by its `signer`.

Then any node takes it at [`POST /api/v1/messages`](/http-api#post-apiv1messages),
like every other message. With [src/delegations.mjs](https://github.com/attestate/kiwistand/blob/main/src/delegations.mjs):

```js
import { Wallet } from "ethers";
import { create, authorization } from "./src/delegations.mjs";
import { sign } from "./src/id.mjs";
import { EIP712_DELEGATION } from "./src/constants.mjs";

const signer = Wallet.createRandom();
const message = create({
  identity: identity.address,
  signer: signer.address,
  authorization: await authorization(signer, identity.address),
  authorize: true,
  timestamp: Math.floor(Date.now() / 1000),
});
const delegation = await sign(identity, message, EIP712_DELEGATION);
// POST delegation to /api/v1/messages
```

The two signatures protect each other. The identity's signature shows it
wants the signer. The signer's signature over the identity's address stops
someone who sees the signer's address from delegating it to themselves and
getting the signer's messages credited to them.

A node takes a delegation if it fits the [Message](/http-api#message) schema,
the signer and the identity differ, the signer signed the authorization for
that identity, and the identity signed the message. Like every message, the
same delegation can be in the trie only once.

:::note
The signer is a new, empty Ethereum account. The delegation only makes Kiwi
News nodes credit the signer's messages to your identity; it gives the
signer no access to your wallet or its funds.
:::

### Smart wallets

A smart wallet (a Coinbase Smart Wallet or Base Account) signs with
[ERC-1271](https://eips.ethereum.org/EIPS/eip-1271), or
[ERC-6492](https://eips.ethereum.org/EIPS/eip-6492) before it's deployed.
Its signature can't be recovered to an address, so nodes check it against
`identity` with viem's `verifyTypedData` over an RPC of the chain the wallet
lives on (`SMART_WALLET_RPC_URL`). An EOA's signature is checked without any
RPC. A node without that RPC doesn't take smart wallets' delegations; whether
every node should check them, or trust the sequencer once a commit lists
them, is an open question.

## Revoking

A revocation is the same message with `authorize` set to `false` and
`authorization` set to `"0x"`: the identity signs it alone. It counts only if
it's signed by the identity the signer signs for at that point in the order.

Nothing is deleted. A revoked signer's messages are still taken and stored,
but from the revocation on, they count for the signer itself, like an
undelegated signer's. What it signed before stays the identity's.

The website doesn't offer revoking yet.

## The order decides

Whom a signer's message counts for depends on where it is in the order of
all messages (see [Order](/protocol#order)), not on timestamps:

- A signer's message counts for the identity of the signer's latest
  delegation before it in the order. If that's a revocation, it counts for
  the signer.
- Messages a signer signed before its first delegation count for that
  delegation's identity.
- A signer delegated again after a revocation, to the same or another
  identity, signs for that identity from then on.

As long as a commit doesn't list a message, its place is provisional: pending
messages come after all committed ones, by timestamp. When a commit lands,
nodes credit the messages of signers with more than one delegation again.

A node resolves the signer of a message when it adds it, when it lists
messages ([`POST /api/v1/list`](/http-api#post-apiv1list) returns each
message's `signer` and `identity`; a delegation's are its own fields), when
it shows a community or counts its members, and for the website's signed
requests (bookmarks, profiles, story analytics), which count as of now.

## From OP Mainnet to the protocol

Before protocol 15.0.0, a delegation was a transaction on OP Mainnet: the
identity sent the signer's authorization (in a domain with `chainId: 10` and
`verifyingContract: 0x418910fef46896eb0bfe38f656e2f7df3eca7198`) to the
Delegator3 contract's `etch(bytes32[3])`, and nodes crawled its `Delegate`
events, on top of the older Delegator2 delegations in
`src/chainstate/historical-delegations.json`. Revocations on OP Mainnet were
always ignored.

At the cutover, all of those delegations go into a snapshot,
`src/chainstate/delegations.json` (signers to identities), made from a node's
delegations with `scripts/delegations-snapshot.mjs`. None are dropped. The
genesis commit holds its keccak-256, and nodes check the file against it. With
the snapshot in place, nodes stop crawling OP Mainnet: the snapshot's
delegations come before every message in the order, and delegation messages
follow. Until the snapshot is in the repository, nodes still crawl OP
Mainnet.

## Accounts without a delegation

A wallet that signs its messages itself needs no delegation; neither does a
passkey account. The website derives a passkey account's key from the
passkey ([`src/web/src/passkey.mjs`](https://github.com/attestate/kiwistand/blob/main/src/web/src/passkey.mjs)),
and that key's address is its own identity.

## Reading delegations

### GET /api/v1/delegations

On the node's `API_PORT` (8443 on news.kiwistand.com). `data` is the
delegations object as of now, signers to identities, both checksummed; a
revoked signer isn't in it:

```json
{
  "status": "success",
  "code": 200,
  "message": "OK",
  "details": "Returning delegations list",
  "data": {
    "0x4E774b8530d6f3A21C449A6f0D9A1229aB2b8C47": "0xee324c588ceF1BF1c1360883E4318834af66366d"
  }
}
```

With `?cached=true`, the response has
`Cache-Control: public, s-maxage=86400, stale-while-revalidate=604800`, and
the node purges that URL from Cloudflare's cache when it takes a delegation.

`resolveIdentity(data, address)` from
[@attestate/delegator2](https://github.com/attestate/delegator2) resolves an
address with it as of now. To read the delegation messages themselves, use
[`POST /api/v1/list`](/http-api#post-apiv1list) with `type: "delegation"`.

## Reference implementation

- [`src/delegations.mjs`](https://github.com/attestate/kiwistand/blob/main/src/delegations.mjs): creating and verifying delegations, and resolving a signer in the order.
- [`src/chainstate/registry.mjs`](https://github.com/attestate/kiwistand/blob/main/src/chainstate/registry.mjs): the snapshot (or, before it, OP Mainnet) and the delegation messages.
- [`src/store.mjs`](https://github.com/attestate/kiwistand/blob/main/src/store.mjs): taking delegations, and resolving the signer when adding and listing messages.
